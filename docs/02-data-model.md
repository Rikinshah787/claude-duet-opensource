# 02 - Data model

Source of truth: `apps/api/duet/models.py`. Engine and session:
`apps/api/duet/db.py`.

Thirteen tables, five enums. The schema is identical on SQLite and Postgres -
`db.py::_make_engine()` only adds `check_same_thread=False` for SQLite. `JSON`
columns map to `json` on SQLite and `JSON` on Postgres via SQLAlchemy's generic
type; nothing in the code relies on `jsonb` operators, so the swap is a
connection string.

All `id` columns are `String(32)` holding `uuid.uuid4().hex`, generated by
`models.py::_uid()`. The one exception is `audit_log.id`, which is an
autoincrementing `Integer` because the chain needs a total order.

`TimestampMixin` adds `created_at` (indexed) and `updated_at` (`onupdate`) to
every table **except `audit_log`**, which is append-only and therefore has no
`updated_at` by design.

Three reference styles coexist, on purpose:

- **Hard FK with `CASCADE`** - everything owned by a user, plus
  `task_steps.task_id` and `approvals.task_id`. Deleting a user deletes their
  whole world.
- **Hard FK with `SET NULL`** - `signals.connection_id`. Disconnecting an app
  must not delete the history of what it told you; the signal survives with a
  null connection and keeps its `connector_key` string.
- **Soft reference** - `messages.task_id`, `messages.approval_id`,
  `messages.signal_id`, `audit_log.user_id`, `workflow_runs.user_id`. These are
  plain `String(32)` columns with no FK. For the audit log that is deliberate:
  a cascade delete must never be able to remove audit rows, and an FK would
  invite exactly that. For `messages` it keeps the thread renderable after the
  referent is gone.

## 2. Enums

Defined as `str`-valued Python enums in `models.py`. **Every enum is persisted
as its `.value` in a plain `String` column**, not as a native DB enum type -
look for `default=TaskStatus.QUEUED.value` in the column definitions. The
trade-off: no DB-level validation, but adding a state needs no migration and
the JSON API serialises without a converter.

### `Disposition` - what the priority engine decided

| Value | Meaning | Set when |
|-------|---------|----------|
| `notify_now` | Interrupt the user now | score >= 72, and >= 88 if in quiet hours |
| `briefing` | Hold for the morning brief | 40 <= score < 72, or >= 72 during quiet hours |
| `defer` | Keep, do not surface | 18 <= score < 40 |
| `ignore` | Recorded, never shown | score < 18 |

Thresholds: `core/priority.py::NOTIFY_THRESHOLD` (72),
`BRIEFING_THRESHOLD` (40), `DEFER_THRESHOLD` (18),
`EMERGENCY_THRESHOLD` (88).

### `TaskStatus`

`queued` · `planning` · `running` · `awaiting_approval` · `blocked` · `done` ·
`failed` · `cancelled`

`blocked` and `cancelled` are declared but never assigned by
`core/orchestrator.py` in the current tree.

### `ApprovalStatus`

`pending` · `approved` · `rejected` · `expired` · `executed` · `reverted`

All six are written. `pending` by `orchestrator._create_approvals()`; the rest
by `core/executor.py` (`decide`, `execute`, `revert`, `expire_stale`). Note that
a failed execution leaves the row at `approved`, not `failed` - there is no
`failed` state, and `execution_result["ok"] is False` is how you tell.

### `RiskTier`

| Value | Scope | Approval behaviour |
|-------|-------|--------------------|
| `safe` | read-only, drafts, internal analysis | still becomes an `Approval` row today |
| `review` | send a message, create a ticket, publish | human decision |
| `sensitive` | money, signatures, deletion, permissions | human decision, explicit |
| `forbidden` | securities trading, inter-account transfers | **blocked; consent cannot unlock it** |

The `forbidden` floor is enforced in two independent places - see
[docs/06-security.md](06-security.md).

### `MemoryKind`

`short` · `long` · `semantic` · `episodic`. Lifetimes and intent are documented
in `agents/memory.py`'s module docstring. `recall()` gives `long` a flat `+0.12`
score bonus so stated preferences stay reachable on a weak lexical match.
`short` and `semantic` are declared but nothing writes them yet:
`capture_preference` writes `long`, `record_episode` writes `episodic`.

## 3. Tables

### `users`

| Column | Type | Notes |
|--------|------|-------|
| `id` | `String(32)` PK | uuid4 hex |
| `email` | `String(320)` | unique, indexed. 320 = RFC-max local+domain |
| `name` | `String(200)` | default `""` |
| `timezone` | `String(64)` | default `"UTC"`. Read by `monitor._local_hour()` via `zoneinfo` |
| `role` | `String(32)` | default `"owner"`. RBAC: `owner` / `member` / `viewer` |
| `quiet_hours` | `JSON` | default `{"start": 21, "end": 7}`. Consumed by `priority._in_quiet_hours()`, which handles the midnight wrap |
| `finance` | `JSON` | default `{}`. The user's own cash figures - `starting_cash`, `monthly_burn`, `ar_collection_rate`, allowlisted on write. Read by `AnalyticsAgent._runway()`, which **refuses to project a runway when it is empty** rather than inventing a balance. Set via `PATCH /api/settings` |
| `briefing_optin` | `Boolean` | default `True` |
| `created_at` / `updated_at` | `DateTime(tz)` | |

`role` is stored but no code reads it yet. RBAC enforcement is on the roadmap,
not in the tree.

### `connections`

One live link to one third-party app for one user.

| Column | Type | Notes |
|--------|------|-------|
| `id` | `String(32)` PK | |
| `user_id` | FK `users.id` ON DELETE CASCADE | indexed |
| `connector_key` | `String(64)` | indexed. Must match a `catalog.CATALOG` key |
| `display_name` | `String(200)` | |
| `status` | `String(32)` | `connected` / `error` / `revoked`. Set to `error` by the sweep on an adapter exception |
| `account_label` | `String(200)` | e.g. the connected mailbox |
| `scopes` | `JSON` list | granted scopes. Checked against `spec.write_scopes` by `security._scope_ok()` |
| `credential_ref` | `String(128)` nullable | **a vault pointer, never a secret.** See `core/vault.py` |
| `enabled` | `Boolean` | default `True` |
| `monitored` | `Boolean` | default `True`. Included in the sweep |
| `last_sync_at` | `DateTime(tz)` nullable | becomes `FetchContext.since` on the next sweep |
| `last_error` | `Text` nullable | truncated to 500 chars |
| `cursor` | `JSON` | incremental sync position, adapter-defined |

**`uq_user_connector` = UNIQUE(`user_id`, `connector_key`)** - one connection
per app per user. Without it, two OAuth round-trips produce two rows and the
sweep fetches the same app twice, creating duplicate work and double-counting
in the brief.

### `signals`

One observed, scored event.

| Column | Type | Notes |
|--------|------|-------|
| `id` | `String(32)` PK | |
| `user_id` | FK `users.id` CASCADE | indexed |
| `connection_id` | FK `connections.id` **ON DELETE SET NULL**, nullable | indexed |
| `connector_key` | `String(64)` | indexed. Denormalised so history survives a disconnect |
| `external_id` | `String(256)` | the vendor's id |
| `kind` | `String(64)` | indexed. One of the ~35 keys in `priority.KIND_WEIGHTS` |
| `title` | `String(500)` | truncated by the sweep |
| `body` | `Text` | default `""` |
| `actor` | `String(256)` | who it came from |
| `url` | `String(1000)` nullable | deep link back to the source |
| `occurred_at` | `DateTime(tz)` | indexed. Vendor timestamp, **not** ingest time |
| `raw` | `JSON` | `{"hints": {...}, **adapter_raw}` as assembled in `monitor._sweep_connection()`. `hints["injection"]` is added by the injection screen when it fires |
| `score` | `Float` | indexed. 0-100, clamped |
| `factors` | `JSON` | `{factor_name: points}` for all 8 factors |
| `reasons` | `JSON` list | human-readable sentences - the "why" the UI shows |
| `disposition` | `String(32)` | indexed. A `Disposition` value |
| `state` | `String(32)` | indexed. `new` / `surfaced` / `handled` / `dismissed` |
| `surfaced_at` | `DateTime(tz)` nullable | when it was actually shown |

**`uq_conn_external` = UNIQUE(`connection_id`, `external_id`) - this is the
sweep's dedupe.** `monitor._sweep_connection()` does not maintain a seen-set;
it inserts optimistically and catches the constraint violation:

```python
db.add(signal)
try:
    db.flush()  # the unique constraint is the dedupe
    created.append(signal)
except IntegrityError:
    db.rollback()
    continue
```

Why in the schema rather than in the application: a demo adapter (and most real
vendor APIs on a cursor reset) replays the same events on every poll. An
in-memory set is lost on restart, is not shared between a scheduler thread and a
manually triggered sweep, and does not protect against two sweeps overlapping.
The constraint holds in all three cases. The scope is `connection_id`, not
`user_id`, so reconnecting an app (new `Connection` row) intentionally lets the
history re-ingest rather than silently going blank.

**`ix_signal_triage` = INDEX(`user_id`, `disposition`, `occurred_at`)** - the
exact shape of the brief's query in `briefing.generate()`: filter by user, filter
by `disposition IN (notify_now, briefing)`, range on `occurred_at`. Without it
that is a full scan of a table that grows by every event in every connected app.

### `task_steps`

One agent turn. This is the trace the Activity view renders.

| Column | Type | Notes |
|--------|------|-------|
| `id` | `String(32)` PK | |
| `task_id` | FK `tasks.id` CASCADE | indexed. `cascade="all, delete-orphan"` on the relationship, `order_by="TaskStep.idx"` |
| `idx` | `Integer` | **0 = planner, 1..N = plan steps, 90 = security review.** The gap is intentional headroom |
| `agent` | `String(64)` | |
| `tool` | `String(128)` nullable | declared; nothing writes it yet |
| `summary` | `String(500)` | the agent's own one-liner |
| `input` | `JSON` | declared; `_begin_step()` does not populate it |
| `output` | `JSON` | **passed through `redaction.redact()` before persisting** (`_end_step`) |
| `status` | `String(32)` | `pending` at construction, then `running`, then `ok` / `error` |
| `error` | `Text` nullable | |
| `duration_ms` | `Integer` | measured with `time.perf_counter()` |
| `started_at` / `finished_at` | `DateTime(tz)` nullable | |

Note the status vocabulary written by the code (`pending` / `running` / `ok` /
`error`) differs from the `StepStatus` union in `apps/web/lib/types.ts`
(`queued` / `running` / `done` / `failed` / `skipped` / `blocked`). The backend
values above are what lands in the database.

### `approvals`

A held action. **Nothing in `payload` has happened yet.**

| Column | Type | Notes |
|--------|------|-------|
| `id` | `String(32)` PK | |
| `user_id` | FK `users.id` CASCADE | indexed |
| `task_id` | FK `tasks.id` CASCADE, nullable | |
| `step_id` | `String(32)` nullable | soft reference, no FK |
| `action_type` | `String(64)` | indexed. Matches a `WriteAction.key` in the catalog |
| `connector_key` | `String(64)` nullable | |
| `risk_tier` | `String(32)` | default `review`. Written from the Security agent's verdict, which comes from the catalog |
| `title` | `String(500)` | |
| `rationale` | `Text` | why the assistant wants this |
| `preview` | `JSON` | **exactly what will happen** - rendered for the human |
| `payload` | `JSON` | the call to execute on approve |
| `status` | `String(32)` | indexed. An `ApprovalStatus` value |
| `reversible` | `Boolean` | default `True` |
| `revert_plan` | `JSON` | populated from `ActionResult.revert_plan` after execution |
| `decided_at` / `decided_by` / `decision_note` | | the human decision |
| `expires_at` | `DateTime(tz)` nullable | `now + settings.approval_expiry_minutes` (default 720 = 12h) |
| `executed_at` | `DateTime(tz)` nullable | |
| `execution_result` | `JSON` | the `ActionResult` after the fact |

`preview` and `payload` are separate columns for a reason: `preview` is what a
person reads and `payload` is what a machine runs. Rendering the payload would
mean the human reviews a serialised API call; keeping them apart means the
preview can be prose while the payload stays executable, and a mismatch between
them is a reviewable bug rather than an invisible one.

| Column | Type | Notes |
|--------|------|-------|

**`ix_memory_lookup` = INDEX(`user_id`, `kind`, `salience`)** - supports
"highest-salience memories of this kind for this user", which is
`ResearchAgent`'s query (`ORDER BY salience DESC LIMIT 6`). Note that
`recall()` itself does **not** use this index: it loads *every* memory row for
the user and ranks in Python, because cosine similarity over a JSON column is
not expressible as an index seek. That is the scaling cliff called out in
[docs/09-roadmap.md](09-roadmap.md).

### `briefings`

| Column | Type | Notes |
|--------|------|-------|
| `id` | `String(32)` PK | |
| `user_id` | FK `users.id` CASCADE | indexed |
| `for_date` | `String(10)` | indexed. `YYYY-MM-DD`. A string, not a date, so it is the user's local day rather than a UTC instant |
| `headline` | `String(500)` | the only part a model writes |
| `sections` | `JSON` list | the rendered brief; see shape below |
| `signal_ids` | `JSON` list | up to 40 ids - provenance for every claim |
| `model` | `String(128)` | `get_llm().provider` at generation time |

Section shape, from `briefing._build_sections()` and `_item()`:

```json
{
  "title": "Money",
  "lead": "Cash and billing",
  "truncated": 0,
  "items": [{
    "id": "…", "title": "…", "detail": "…", "actor": "…",
    "connector": "quickbooks", "kind": "invoice_overdue",
    "score": 71.2, "why": "41 days overdue; $18,400 at stake",
    "when": "2026-10-26T…", "url": null
  }]

```

Storing the rendered brief rather than regenerating it means a brief you read
last Tuesday still says what it said last Tuesday, even after the underlying
signals are handled or the weights are retuned.

### `audit_log`

Append-only, hash-chained. Any gap or edit breaks verification.

| Column | Type | Notes |
|--------|------|-------|
| `id` | `Integer` PK autoincrement | the chain's total order |
| `at` | `DateTime(tz)` | indexed |
| `user_id` | `String(32)` nullable | indexed. **No FK** - a user cascade must never delete audit rows |
| `actor` | `String(100)` | `system` / `agent:planner` / `agent:security` / `user` |
| `action` | `String(100)` | indexed. See the full vocabulary below |
| `resource_type` / `resource_id` | `String(64)` | |
| `outcome` | `String(32)` | default `ok` |
| `detail` | `JSON` | **always passed through `redaction.redact()` in `audit.record()`** |
| `prev_hash` | `String(64)` | the previous row's `hash` |
| `hash` | `String(64)` | `sha256(f"{prev_hash}|{canonical_json(row)}")` |

No `TimestampMixin`: there is no `updated_at`, because a row is never updated.

Every `action` value written anywhere in the tree:

| `action` | `actor` | Written by |
|----------|---------|------------|
| `task.started` | `agent:planner` | `orchestrator.run_task` |
| `task.finished` | `agent:planner` | `orchestrator.run_task` |
| `task.failed` | `agent:planner` | `orchestrator.run_task` (exception path) |
| `approval.requested` | `agent:security` | `orchestrator._create_approvals` |
| `approval.approved` | `user:<email>` | `executor.decide` |
| `approval.rejected` | `user:<email>` | `executor.decide` |
| `approval.refused_at_execution` | `system` | `executor.execute` (preflight failed) |
| `approval.expired` | `system` | `executor.expire_stale` |
| `action.executed` | `system` | `executor.execute` |
| `action.failed` | `system` | `executor.execute` |
| `action.reverted` | `user:<email>` | `executor.revert` |
| `monitor.sweep` | `system` | `monitor.sweep_user` |
| `security.injection_detected` | `system` | `monitor._sweep_connection` - `outcome` is `"hostile"` or `"flagged"`, `resource_id` is the signal's `external_id` |
| `briefing.generated` | `system` | `briefing.generate` |
| `connector.connected` | `user:<email>` | `api/apps.py::connect` |
| `connector.disconnected` | `user:<email>` | `api/apps.py::disconnect` |
| `admin.reset` | `user:<email>` | `api/system.py::admin_reset` - the record that everything was erased |

That is the whole list - 17 actions. Anything the assistant did that is not in
this table is not in the chain, which is itself a reviewable property because
the table is short enough to read.

Note `admin.reset` deliberately survives the reset it records:
`POST /api/admin/reset` erases the user's signals, tasks, approvals, messages,
memories, connections and vault credentials, and leaves the audit chain intact.
Truncating the chain to hide the erasure would break verification for every row
after it.

The digest covers `action`, `actor`, `user_id`, `resource_type`,
`resource_id`, `outcome` and `detail` - serialised with `sort_keys=True` so the
digest is stable across dict ordering. It does **not** cover `at`, so
back-dating a row does not break verification. That is a known gap, recorded in
[docs/06-security.md](06-security.md).

`verify_chain(db, limit=None)` recomputes the whole chain and returns either
`{"valid": True, "checked": N, "head": "<16 hex chars>"}` or
`{"valid": False, "checked": N, "broken_at": <id>, "at": "<iso>"}` - the first
break, not a list.

### `policy_rules`

User-tunable overrides for the priority engine and the approval gate.

| Column | Type | Notes |
|--------|------|-------|
| `id` | `String(32)` PK | |
| `user_id` | FK `users.id` CASCADE | indexed |
| `kind` | `String(32)` | `vip` / `mute` / `boost` / `never` |
| `pattern` | `String(300)` | email, domain, connector key or keyword. Matched as a **plain substring**, lowercased - not a regex |
| `weight` | `Float` | default `1.0`, multiplies the rule's points |
| `note` | `String(300)` | |
| `enabled` | `Boolean` | default `True` |

Where each kind is consumed:

| `kind` | Consumer | Effect |
|--------|----------|--------|
| `mute` | `priority.preference_factor` | `-40 * weight` |
| `boost` | `priority.preference_factor` | `+18 * weight` |
| `vip` | `priority.preference_factor` **and** `monitor.sweep_user` (builds the `vips` set for `relationship_factor`, worth `+20`) | both |
| `never` | `agents/security.py::review` step 4 | blocks the action outright: *"You asked me never to {pattern}."* |
There are exactly four kinds, and all four have a consumer. `auto_approve` was
accepted by the API at one point and read by nothing; it has been removed from
`NewRule`'s validation pattern (`^(vip|mute|boost|never)$`), so posting it now
returns `422`. **There is no way to configure the system to act without a human
decision** - that is a property of the code, not a default you can change.
Pinned by `tests/test_safety.py::TestReviewRegressions::test_auto_approve_rule_is_not_accepted`.

Durable state for the workflow engine. Survives a restart mid-flight.

| Column | Type | Notes |
|--------|------|-------|

**Status:** `core/scheduler.py` defines `schedule(db, user_id, workflow_key,

helpers exist, and nothing writes a row yet. The module comment names it: *"the
seam Temporal would replace."* See [docs/07-workflows.md](07-workflows.md).

## 4. Lifecycle: a `Signal`

```
                  adapter.fetch() returns a RawSignal
                              │
                              ▼
      injection.screen_signal(title, body) → InjectionReport
          suspicious → raw.hints["injection"] = {...}
                       audit "security.injection_detected"
                              │
                              ▼
                 priority.score_signal() → Verdict
                              │
                              ▼
         ┌────────────────────────────────────────────┐
         │  INSERT signals (state="new",              │
         │                  disposition=<verdict>)    │
         │  on uq_conn_external violation → skip      │
         └──────────────────┬─────────────────────────┘
                            │
         ┌──────────────────┼──────────────────────────┐
         │                  │                          │
  disposition =      disposition =            disposition =
  notify_now         briefing                 defer / ignore
         │                  │                          │
         ▼                  ▼                          │
  monitor._maybe_      briefing.generate()             │
  interrupt()          picks it up within              │
  (top 1 by score)     lookback_h (24h)                │
         │                  │                          │
         └────────┬─────────┘                          │
                  ▼                                    ▼
      state = "surfaced"                     state stays "new"
      surfaced_at = now                      (never shown; still
                  │                           counted by analytics
                  │                           and still queryable)
                  ▼
        ┌───────────────────────────┐
        │  the user does something  │
        └────────┬─────────┬────────┘
                 ▼         ▼
        state="handled"  state="dismissed"
                 │         │
                 └────┬────┘
                      ▼
      memory.behaviour_history() counts them per kind
                      │
                      ▼
      priority.historical_factor() on the NEXT signal of that kind:
         handled/total >= 0.70  →  +10  "you usually act on X"
         handled/total <= 0.25  →  -14  "you usually dismiss X"
         total < 3              →    0  (not enough evidence)
```

Three notes on this loop:

1. `handled` and `dismissed` are written by three endpoints in
   `api/work.py`: `POST /api/signals/{id}/dismiss` (→ `dismissed`),
   `POST /api/signals/{id}/handle` (→ `handled`) and
   `POST /api/signals/{id}/act` (→ `handled`, and spawns a task). That closes
   the feedback loop into `historical_factor`, which needs at least 3 outcomes
   of a kind before it contributes any points.
2. `briefing.generate()` also promotes `new` → `surfaced` for everything it
   includes, so a brief is a surfacing event, not just a read.
3. `disposition` is never recomputed. A signal scored at 3am during quiet hours
   is stamped `briefing` and stays `briefing` even if the same event would score
   `notify_now` at noon. Re-scoring on read would make the brief
   non-reproducible; the cost is that a stale verdict can outlive its context.

## 5. Lifecycle: an `Approval`

```
  Agent returns a Proposal
       │
       ▼
  SecurityAgent.review()
       │
       ├── FORBIDDEN_ACTIONS hit            → never becomes a row
       ├── catalog risk == forbidden        → never becomes a row
       ├── scope check failed               → never becomes a row
       ├── egress check failed              → never becomes a row
       ├── PolicyRule(kind="never") hit     → never becomes a row
       │       (all five land in task.result["blocked"] and are told to
       │        the user verbatim in the thread message)
       │
       └── cleared
             ▼
       INSERT approvals (status="pending",
                         risk_tier=<from catalog>,
                         expires_at = now + 12h)
       audit: approval.requested
             │
      ┌──────┴───────────────────────────────┬─────────────────────┐
      ▼                                      ▼                     ▼
  POST /approve                        POST /reject       executor.expire_stale()
  executor.decide(True)                executor.decide(False)  (housekeeping,
      │                                      │                   every 300s)
      │  refuses with ExecutionRefused       │                     │
      │  → HTTP 409 if status != pending     │               status="expired"
      │                                      ▼               audit: approval.expired
  status="approved"                   status="rejected"      _settle_task()
  decided_at / decided_by / note      decided_at / note
  audit: approval.approved            audit: approval.rejected
      │                               thread: "Rejected. Nothing was
      ▼                                        sent or changed."
  executor.execute() → _preflight()
      │
      ├── preflight refuses (forbidden verb, catalog-forbidden,
      │   connector gone/disabled, expired)
      │        status="rejected"
      │        execution_result = {"ok": false, "error": "..."}
      │        audit: approval.refused_at_execution  (outcome="refused")
      │        thread: "I couldn't carry that out: <reason>"
      │
      └── preflight passes
             registry.resolve(connector_key)
             FetchContext(credential=CredentialHandle(conn.credential_ref, key))
             adapter.execute(action_type, payload, ctx)
             (adapter exceptions are caught → ActionResult(ok=False,
                                               error="adapter_error"))
                │
                ├── ActionResult.ok = True
                │        status="executed",  executed_at = now
                │        execution_result = {ok, summary, data, external_id}
                │        revert_plan = ActionResult.revert_plan
                │        audit: action.executed
                │        thread: the adapter's own summary
                │          │
                │          └── POST /revert → executor.revert()
                │                requires status == "executed", reversible,
                │                and a non-empty revert_plan, else 409
                │                adapter.execute(revert_plan["action"], plan, ctx)
                │                on ok → status="reverted", audit: action.reverted
                │
                └── ActionResult.ok = False
                         status stays "approved" (NOT failed)
                         execution_result carries the error
                         audit: action.failed  (outcome="error")
                         thread: "That didn't go through: <summary>"

  after every terminal transition:  _settle_task()
      if the parent task is AWAITING_APPROVAL and no sibling approval is
      still PENDING  →  task.status = DONE, finished_at = now
```

Implementation notes that matter when reading the table:

- **`decide()` is the only entry point** from the API. It refuses non-`pending`
  rows with `ExecutionRefused`, which `api/work.py` maps to HTTP 409. A
  double-click cannot execute twice.
- **A failed execution does not get its own status.** The row sits at `approved`
  with `execution_result["ok"] == false`. Deliberate - "approved but the vendor
  rejected it" is a different situation from "the human said no" - but it means
  `status == "approved"` is ambiguous without reading `execution_result`.
- `expire_stale()` sets `expired` on any `pending` row past `expires_at`. The
  docstring states the intent: *"Approvals that sat too long are expired rather
  than silently executed later."* It runs from the scheduler's housekeeping loop
  every 300 seconds, and `_preflight` checks expiry again anyway.
- A live adapter returns a `revert_plan` only for actions it can genuinely
  undo - `notion.delete_page` ships one that un-archives, because deleting in
  Notion means archiving. `POST /revert` returns 409 on anything else, with a
  message naming the app you have to go fix it in by hand.
- `BaseConnector.execute()` returns
  `ActionResult(ok=False, error="not_implemented")`, so a catalog entry with no
  adapter fails closed rather than silently succeeding.

### `reversible` comes from the catalog, like `risk`

`reversible` is declared in two places - on the `Proposal` by the proposing
agent, and on the `WriteAction` in the catalog - and **the catalog wins**, the
same way it does for `risk`. From `orchestrator._create_approvals()`:

```python
# ... risk and reversible are both declared in the catalog, which is the one
# place they are declared. Taking risk from the catalog but reversible
# from the proposing agent would let an agent claim an irreversible
# action is undoable.
reversible = p.reversible
if declared is not None:
    reversible = declared.reversible
```

The agent's value survives only when the catalog has no `WriteAction` for that
verb. So an agent cannot mark `send_email` undoable and produce a Revert button
backed by a revert plan that was never created.

Pinned by
`tests/test_safety.py::TestReviewRegressions::test_reversibility_comes_from_the_catalog_not_the_agent`.

## 6. Creating the schema

```python
from duet.db import init_db
init_db()          # Base.metadata.create_all(bind=engine)
```

There is no migration tool in the tree - no Alembic, no versions directory.
`create_all` is additive only: it creates missing tables and does nothing to
existing ones. Changing a column today means dropping `.data/duet.db`.

For a deployment that needs to keep data across schema changes, Alembic is the
gap; see [docs/09-roadmap.md](09-roadmap.md).
